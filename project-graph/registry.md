# registry

**What:** [[core-api]] module owning companies, users (real signup/login since M3.1 — no longer "dev-mode"), role_definitions (versioned, global templates have `company_id NULL`), agents CRUD + roster, manager-hierarchy validation (acyclic).

**+ M3.4 (2026-07-17 session 30): 3 more global role templates, data-only.** `V9__seed_starter_roster_templates.sql` adds `lead`/`product`/`content` alongside M0.2's `coder`/`tester`/`research` (company_id NULL, generic prompts) — for [[web-dashboard]]'s new onboarding wizard's starter packs, and reusable afterward via the ordinary Invite Agent flow too. `lead`/`product` both carry `allowed_tools:["create_child_tasks"]` (M2.2's tool), no code changes needed anywhere to grant it. Zero Java touched.

**+ M3.1 (2026-07-16 session 29): real auth, dev headers gone.** New `AuthService`/`AuthController` (`POST /auth/signup`/`/auth/login`) — signup creates the company (delegates to the existing `CompanyService.create`) + first admin `User` (new `password_hash` column, BCrypt) atomically and issues a JWT (`common.JwtService`); login re-verifies + reissues. `CompanyController`'s old standalone `POST /companies` bootstrap is **deleted** — signup is the only company-creation path. New `UserRepository.findByEmail` (login is global-by-email, company isn't known yet). `AgentDirectory` gained `companyIdOf(agentId)` — the one deliberate exception to "no method without a companyId param," used only so the Worker API gateway (`X-Agent-Id`) can resolve its own tenant without depending on a human JWT at all (previously it accidentally did, via the old blanket-header rule). Every module that reads `TenantContext` is otherwise unchanged — the JWT-vs-header swap happened entirely in `common.TenantContextFilter`, not here.

**State: SKILL-ATTACH-WIRED (M0.2+M0.5b+M0.7+M-SK1, 2026-07-14 session 13).** M-SK1 adds one new interface, `RoleSkillAttachment` (registry-owned, agentmind-implemented — see [[agentmind]] for the full boundary reasoning): `AgentService.hire()` now calls `roleSkillAttachment.attachTemplateSkills(companyId, agentId, roleDefinition.getId())` right after `agents.save(agent)`, same transaction. `RoleDefinitionLookup` gained a company-scoped `findVisibleToCompany(companyId, id)` (agentmind's role-skill-attach endpoint needs to verify tenant ownership of an untrusted role-definition id, unlike the pre-existing `findById` whose only caller already held a trusted row). M0.7 added one interface method, `AgentDirectory.pauseForBudget(companyId, agentId)` (JpaAgentDirectory impl: sets `paused=true` + calls `AgentLifecycleService.stop`, no-op if already paused) — everything else below is unchanged since M0.5b. Entities+repos (`registry/domain`, every repo method companyId-scoped), endpoints per 04 §Registry + 16 §1 (hire/patch with runtimeType/runtimeConfig/paused, roster, profile w/ zeroed stats, role-definitions, `/model-catalog` prices omitted), `AgentRuntime` SPI in `registry/runtime` (verbatim 13 §3.1). At M0.5b: the M0.2 `LlmLoopRuntimeDescriptor` placeholder bean is **gone**, replaced by execution's real `LlmLoopRuntime`; new `AgentLifecycleService` (start on hire/unpause, stop on pause — deferred to `afterCommit` via `TransactionSynchronizationManager` so a poll tick never races the enclosing hire/patch tx) wired into `AgentService.hire()`/`patch()`; new `RoleDefinitionLookup` (+ Jpa impl) — same cross-module pattern as `AgentDirectory`/`ModelCatalogLookup` — lets execution's PromptAssembler read system_prompt/output_contract without touching the repo; `AgentDirectory.findById` used by the loop to re-read the roster row every tick (never cached). `AgentDirectory.findBySkill` impl, `V2_1__seed.sql` (coder/tester/research templates + 3 anthropic model_catalog rows). 50 ITs green (repo-wide) incl. isolation + manager-cycle. Runtime SPI still lives in registry (not execution) to keep the dependency direction acyclic.

**Rev C additions ([[agent-platform]]):** owns `model_catalog` (+ `GET /model-catalog`); agents gain `runtime_type`/`runtime_config` (validated against RuntimeRegistry on hire/patch → 400) and `paused`; hire auto-attaches the role template's skill set (M-SK1, live — see [[agentmind]]).

**+ M-AR1 (2026-07-16 session 28): runtime-axis pluggability proven, zero diff here.** [[execution]]'s new `EchoRuntime` bean (a second `AgentRuntime` implementation) was picked up by `RuntimeRegistry`'s `List<AgentRuntime>` injection and `AgentService.hire()`'s already-generic `runtimeRegistry.validate(runtimeType, runtimeConfig)` with **no code change in this module at all** — the "roles are data" pattern already documented above for skills turns out to hold identically for runtimes. See [[execution]] for the build.

**Key rules:** hire via template key or explicit role_definition; skill_tags non-empty; manager cycles rejected. Exposes `AgentDirectory` interface for [[routing]] to validate skills, and now (M0.7) for [[accountability]]'s `BudgetService` to auto-pause an over-cap agent (`AgentDirectory.pauseForBudget`) — other modules never import registry internals. **`JpaAgentDirectory` injects `AgentLifecycleService` `@Lazy`:** that service sits behind `RuntimeRegistry → LlmLoopRuntime → WorkBroker → AgentDirectory`, so an eager constructor injection there would be a circular bean dependency at context startup — the lazy proxy defers resolution past boot. **Roles are data**: adding a role must never touch router code (proven at M1.1).
