# accountability

**What:** [[core-api]] module owning budgets ("payroll"), approvals, the append-only `task_events` audit log, usage metering, and analytics rollups.

**State: + shared usage-ledger (M-LN1, 2026-07-15 session 16).** New `UsageLedger` interface + `UsageLedgerService` impl — the `usage_records` insert-once-then-`recordSpend` logic that used to live inline inside `execution.UsageRecorder` moved here, since [[agentmind]]'s new `LearningPipeline` needs the identical dup-guard behavior for its own `learn:{eventId}`-keyed extraction calls, and `agentmind` may depend on `accountability` but never on `execution` (12 §2 — boundary rule added this session). `execution.UsageRecorder` now just computes the `taskId:attempt` key and delegates here; its own behavior/tests are unchanged. See [[agentmind]] for the full M-LN1 story.

**Earlier — BUDGET ENFORCEMENT LIVE (M0.7, 2026-07-13 session 6f).** `BudgetService implements BudgetGuard, BudgetLedger` replaces `NoopBudgetGuard` (deleted). New `accountability/domain/Budget` entity (03/15's `budgets` table + new `alerted_at TIMESTAMPTZ` column, `V3__budget_alerted_at.sql`) + `BudgetRepository`. `canSpend(companyId, agentId)` — consulted inside [[routing]]'s claim tx exactly as before — checks BOTH the agent's own cap and the company-wide cap (`agent_id IS NULL` row) for the current period (`YearMonth.now(clock)`); a missing row for either scope means that scope is uncapped (budgets are opt-in). **Design call:** an agent-scope breach auto-pauses that agent (`AgentDirectory.pauseForBudget`, new interface method) via [[registry]]'s existing `AgentLifecycleService.stop`; a company-wide breach refuses the claim WITHOUT pausing any single agent, since the cap is shared and picking one to punish would be arbitrary. **Real bug caught by the tests, not by inspection:** the auto-pause + `budget.exceeded` outbox write can't happen inside `canSpend`'s own transaction, because `PostgresWorkBroker.claim` immediately throws `ConflictException` right after `canSpend()` returns false to produce the 409 — and that throw rolls back the WHOLE transaction, silently undoing the pause and the event. Fixed by extracting both into new `BudgetBreachRecorder` (`@Transactional(propagation = REQUIRES_NEW)`), which commits independently of whatever the caller's claim transaction does next. `UsageRecorder.record` (execution) now calls `BudgetLedger.recordSpend` — but ONLY when the idempotent insert actually wrote a new row, so a deduped redelivery never double-counts spend even though `usage_records` itself already guards the double-bill case. `recordSpend` increments both scopes' `spent_tokens` and, crossing `alert_pct` (default 80) for the first time this period (`alerted_at IS NULL`), emits `budget.threshold` once — the natural `(company_id, agent_id, period)` UNIQUE key means a new period gets a new row and the dedupe resets for free. **Circular-dependency gotcha:** wiring `pauseForBudget` into `JpaAgentDirectory` needed `AgentLifecycleService` — but that sits behind `RuntimeRegistry → LlmLoopRuntime → WorkBroker → AgentDirectory`, an eager cycle at context startup; fixed with `@Lazy` on that one constructor parameter. New `accountability/api/BudgetController` — `GET/PUT /companies/{id}/budget`. `StatsRollup` still not started (M2.3).

**Rev C additions ([[agent-platform]]):** budget tiers per Paperclip — `budgets.alert_pct` soft alert (`budget.threshold` event, once per period) + hard cap now **auto-pauses** the agent (`agents.paused`) besides refusing claims — DONE at M0.7 above; usage idempotency namespaces widen to `taskId:attempt` / `learn:` / `embed:` (learning + embeddings are metered payroll too, still pending); StatsRollup becomes a durable outbox consumer at M2.3.

**Key components:**
- `BudgetGuard.canSpend(companyId, agentId)` / `BudgetLedger.recordSpend(companyId, agentId, tokens)` — both implemented by `BudgetService` (accountability). Real cap check + over-cap → claim refused + `budget.exceeded` outbox event + auto-pause is DONE (M0.7) — see State above for why "flag the task" (17's literal wording) was deliberately NOT implemented as a `task_events` row: `queued→flagged` isn't a legal `TaskStateGuard` edge, and flagging a shared queue item would wrongly block OTHER agents from claiming it over one agent's budget.
- `UsageRecorder.record()` — lives in [[execution]], not here (M0.5b design call — it's called directly from `LlmLoopRuntime`, same tx as `TaskService.complete()`); calls `BudgetLedger.recordSpend` as of M0.7.
- `StatsRollup` — updates `agent_stats_daily` on approve/reject + nightly. Success rate = approved ÷ (approved+rejected). Not started — M2.3.

**Hard rules:** `task_events` is append-only — never UPDATE/DELETE. `pending_review` is a hard gate; nothing ships unreviewed.
