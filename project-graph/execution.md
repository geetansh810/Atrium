# execution

**What:** [[core-api]] module that does the actual AI work: `LlmClient` interface (AnthropicClient / OpenAiClient / GeminiClient, selected per agent row), `AgentRunner` (one loop per active agent, virtual threads), `PromptAssembler`.

**State: + M-LOG1 (2026-07-23 session 34) — LLM request logging at the single doorway.** New `LlmRequestLogService` + `LlmRequestLog` entity/repo (`execution/domain`) + `LlmRequestLogController` (`GET /companies/{id}/llm-logs` list + `/{logId}` detail) + `LlmLogRetentionJob` (nightly purge, `ATRIUM_LLM_LOG_RETENTION_DAYS` default 30). `LlmRouter.complete()` — the one place every provider call routes — now records each call once (after retries, with total latency) on success and final error, in a `@Transactional(REQUIRES_NEW)` best-effort write that swallows its own failures (a logging error must never break the LLM call) and only fires when a tenant is bound (agent loop's `runAsSystem`), so RLS's `app.company_id` is set; `agentId`/`taskId` come from the MDC (`LogContext`). New `V14__llm_request_logs.sql` ([[data-model]]) captures the full system_prompt/messages/tools/response/tool_calls + tokens/latency/status/error — distinct from `usage_records` (billing) and `task_events` (audit); learning-extraction calls under RLS bypass aren't logged (no bound company — documented limitation). Frontend `/logs` page in [[web-dashboard]]. **Verification partial:** router unit test green, compiles, mock-mode UI verified; the 3 new `LlmLoopRuntimeTest` integration cases + API-mode live check couldn't run (Docker unresponsive this session).

**Earlier — M-AR1 (2026-07-16 session 28) — a second `AgentRuntime` bean, `EchoRuntime`, proves the runtime axis is genuinely pluggable.** Same one-virtual-thread-per-agent poll shape as `LlmLoopRuntime` (`type()="echo"`), but claims a task and completes it with a canned artifact — no LLM call, no context assembly, no usage recording (nothing real to meter). Auto-discovered by [[registry]]'s `RuntimeRegistry` (Spring `List<AgentRuntime>`) purely by being a `@Component`; `AgentLifecycleService`/`AgentService.hire` were already fully generic over `runtime_type` since M0.5b, so adding this bean required **zero changes to routing/, registry/ (minus seed), or any migration** — verified via `git diff --stat` before committing, the literal Done-when. Fat-claim (`ContextBundle` in the Worker API's claim response, 16 §5) was deliberately deferred, docs-first (17's M-AR1 card amended) — `EchoRuntime`, like `llm_loop`, never calls `WorkerTaskController`'s HTTP gateway, so there's no real caller for `contextMode='fat'` yet; building it now would have meant editing `routing/api/WorkerTaskController.java`, directly breaking this milestone's own empty-diff proof. `WorkerTaskController`'s existing "Fat-claim ContextBundle lands at M-AR1" comment is now known-stale and intentionally left untouched — flagged for whichever future session actually builds `webhook`/`process`.

**Earlier — M2.2 (2026-07-15 session 21) — the first real tool: `create_child_tasks`.** New `ChildTaskTool` (`execution.ChildTaskTool.DEF`) is offered to the model in `LlmLoopRuntime.runOnce`'s `LlmRequest.tools` list IFF the claimed task's `RoleDefinition.allowedTools` JSON array lists its name — a data-driven gate (roles are data, no role-key branching), populated from a column ([[registry]]'s `role_definitions.allowed_tools`) that had existed unused since M0.2. Single-shot: if the model's response carries a `create_child_tasks` tool call, `runOnce` calls [[routing]]'s new `TaskService.completeWithDecomposition` instead of `complete` — one transaction, same usage-record idempotency as the non-tool path. Deliberately NOT a multi-turn tool loop (`maxToolTurns` stays unused) — a real back-and-forth would need the assistant's `tool_use` content block replayed verbatim into the next request's message history (Anthropic's protocol requires it precede the matching `tool_result`), which `execution.spi.LlmMessage`'s plain-string `content` field can't carry; deferred until a real multi-turn use case needs it. Verified live: a real Gemini call against the Agrawal Namkeen tenant's PM role (a new role-definition version with `allowedTools:["create_child_tasks"]`) genuinely invoked the tool and spawned 2 real child tasks.

**Key rules:**
- `PromptAssembler.build(roleDef, task, feedback?, bundle?)` is a **pure function that only sees those four inputs** — secrets structurally impossible in prompts. Rejection feedback included on retry (M0.6: [[routing]]'s `TaskService.latestRejectionFeedback` on every claim). Context bundle included since M-CTX1 ([[agentmind]]'s `ContextAssembler`, assembled inside the claim's own transaction so its provenance rides along same-tx with the `claimed` audit event).
- Every LLM call → `usage_records` insert with idempotency key `taskId:attempt` in the same tx ([[accountability]]) — redelivery never double-bills.
- Provider failure → `TaskService.flag()`, never crash the runner. Completion → artifact row + `pending_review`.
- API keys from env only, never logged.
