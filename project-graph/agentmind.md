# agentmind

**What:** [[core-api]] module owning the skills registry (14 §1), the memory store (14 §2), knowledge ingestion (14 §3), and the learning pipeline (14 §5) — the "depth" subsystem ([[agent-platform]]: skills → memory → knowledge → learning). All five milestones of that series (M-SK1/M-CTX1/M-MEM1/M-LN1/M-KN1) are live; a real embeddings-degrade bug in the learning pipeline was found and fixed post-hoc (M-LN2-fix, session 27).

**State: M-LN2-FIX — embeddings-readiness bug fixed, learning pipeline verified live without an OPENAI_API_KEY (2026-07-16, session 27).** `PgVectorMemoryStore.ingest()` used to call `embeddingClient.embed()` with no `isReady()` guard (unlike `recall()`/`findDuplicate()`, which already degraded gracefully), and separately `LearningPipeline.handle()` had its own unconditional `isReady()` early-return — together these meant the pipeline silently skipped every trigger event and never wrote a memory row in any session's environment to date (none has ever had `OPENAI_API_KEY`). Fixed by giving `ingest()` the same degrade posture (`embedOrDegrade()`: NULL embedding instead of throwing when the provider isn't ready or a live call fails — the schema's `embedding` column is nullable for exactly this) and deleting `LearningPipeline`'s `EmbeddingClient` dependency and gate entirely — the degrade decision now lives solely at the one call site that actually needs it. Also fixed `MemoryService.seed()` (the human-authored `POST /companies/{id}/memories` path), the other real caller of `ingest()` that had no gate at all and previously 400'd without a key. New tests: `LearningPipelineTest.extractionStillWritesGovernedMemoriesWhenEmbeddingsAreNotConfigured` (reject→governed writes land with NULL embeddings, still metered, `embed()` proven never-called; re-stubbing `isReady()`→true mid-test proves the row still isn't recallable — the SQL's own `embedding IS NOT NULL` filter, not just the client gate, is what excludes it), `MemoryApiTest.seedingSucceedsWithoutAnEmbeddingsProviderConfigured`. **Done-when verified LIVE against the real Agrawal Namkeen tenant, not just tests:** rebuilt core-api, real task → Priya (`google`/`gemini-3.1-flash-lite`) completed it → rejected with brand+style feedback → within one poll tick the review-queue held 2 real `pending_review` items (`extractedBy:"pipeline"`), confirmed via Postgres that all 4 new memory rows (2 pending + 2 auto-active agent summaries) carry `embedding IS NULL`; approved one via the real review endpoint, confirmed it flipped `active` and left the queue. 151/151 core-api tests green across two full-suite reruns (one earlier run showed the new test failing fast alongside heavy background-thread connection-reset noise from OTHER test classes sharing the reused Testcontainers Postgres — reproduced as pre-existing full-suite flakiness, same class already documented for `MemoryRecallPerformanceTest`, not caused by this fix: passed cleanly and repeatably in isolation and in two clean full-suite reruns after). **Earlier — LEARNING PIPELINE + REVIEW GOVERNANCE LIVE (M-LN1, 2026-07-15 session 16).** New `LearningPipeline extends eventbus.EventCursorWorker` — the first real subclass of that M0.75 base class, consuming `task.rejected|approved|completed`. Per event: builds an `ExtractionContext` (agent + its role + a `tier='fast'` catalog entry for the SAME provider the agent already uses — new `ModelCatalogLookup.findByProviderAndTier`), calls `execution.spi.LlmClient` with a structured-output (`jsonSchema`) request asking for `{items:[{content,kind,scope}]}` (rejected/approved) or `{summary}` (completed, forced `kind='summary', scope='agent'` regardless of what the model would've said). `decideStatus(scope, kind)` is the ONE place governance is decided — auto-`active` only for `agent`-scope `lesson`/`summary`, everything else (every `role`/`company` write, every `fact` regardless of scope) lands `pending_review` — never trusting the extraction model's own tagging for this call. Before every insert, a new `MemoryStore.findDuplicate` (exact-scope match, ≥0.92 cosine similarity — a much higher bar than `recall()`'s 0.30 relevance threshold) either bumps `importance` (capped at 5) or lets the insert proceed; `memory.learned`/`memory.review_requested` (+ a `bot.notice`) outbox events follow, new `Topics.memory(companyId, agentId)`. New review-queue (`GET .../memories/review-queue`) + review-action (`POST /memories/{id}/review`) endpoints on `MemoryService`/`MemoryController`: approve/reject a `pending_review` item, optionally `promoteScope` (new `MemoryStore.promoteScope`, resolves the agent's role key when promoting agent→role) and/or `asSkill` (spins off a `trust_level='agent_proposed'` draft skill via a new `SkillService.createDraftFromMemory` — never auto-promoted to `platform`/`company` trust, stays inert until a human separately promotes it, same as any other `agent_proposed` row). **Design call — extraction calls are metered like any LLM call (14 §5 "learning is payroll too"), but `agentmind` must never import `app.atrium.execution` (12 §2):** solved by extracting a new `accountability.UsageLedger` interface (+ `UsageLedgerService` impl) out of what used to be `execution.UsageRecorder`'s own inline JDBC insert — `UsageRecorder` now just supplies the `taskId:attempt` key format and delegates, `LearningPipeline` supplies `learn:{eventId}` instead; both share one insert-once-then-record-spend implementation. Cost math (`LlmCostCalculator`'s 3-line formula) is duplicated rather than shared, for the same import-boundary reason. New boundary rule `agentmind → accountability (UsageLedger)` added to 12 §2 alongside `agentmind → execution.spi (LlmClient only)`. **Design call — `agentId` added to `task.completed`/`task.rejected`/`task.approved` outbox payloads** (additive, 16 §4): by the time this async durable consumer processes a `rejected` event, `tasks.assigned_agent_id` is already NULL (`TaskService.reject()` clears it in the same tx that writes the event), so the payload is the only reliable place left to find "whose work is this." **Two real bugs caught before/by the tests, not by inspection:** (1) `EventCursorWorker`'s constructor-param repository types were package-private — harmless until this milestone's `LearningPipeline` became the first subclass declared OUTSIDE `eventbus`, at which point it wouldn't even compile; made both `OutboxEventRepository`/`EventConsumerCursorRepository` public. (2) A classic Spring self-invocation trap: `LearningPipeline`'s own `@Scheduled poll()` calling the inherited `@Transactional pollOnce()` via plain `this.pollOnce(...)` would silently skip the proxy, meaning no transaction ever opens and every `MANDATORY`-propagation write inside `handle()` throws at runtime — fixed with a `@Lazy` self-injected proxy reference (same idiom `JpaAgentDirectory` already uses for its own circular-dependency case). (3) `MemoryService.review()`'s final read used JPA `findById` after several raw-JDBC writes to the SAME row already sitting in the persistence context's cache (`PgVectorMemoryStore`'s whole-class raw-JDBC convention) — silently returned the pre-mutation snapshot; fixed with `entityManager.refresh(memory)`. Done-when verified: reject a task with feedback "never use passive voice; our brand name is X-Corp" → an auto-active agent-scope lesson AND a pending company-scope fact (new `LearningPipelineTest`, WireMock-backed extraction); approving the fact makes it recall for a different agent (company scope is unconditionally in every recall scope-set); replaying the same event via a rewound consumer cursor creates no new memory or `usage_records` row (dedup bump instead); a rejected memory never appears in recall (new `MemoryApiTest` cases). 115/115 core-api tests green (3 skipped, unchanged live-key tests). `make check` clean.

**Earlier — MEMORY STORE + RECALL LIVE (M-MEM1, 2026-07-15 session 15).** `EmbeddingClient` SPI + `OpenAiEmbeddingClient` (REST, key `OPENAI_API_KEY`, default `text-embedding-3-small`/1536-dim) — `isReady()` false means degrade, never throw, same pre-dispatch-gate contract as [[execution]]'s `ProviderReadiness` but added directly to this (non-frozen) interface. `PgVectorMemoryStore implements MemoryStore` (ingest/recall/forget/setStatus) — raw JDBC throughout, no Hibernate vector-type mapping (the `Memory` entity excludes the `embedding` column entirely; only this class ever reads/writes pgvector text literals, cast via `::vector` in SQL — same "raw SQL for Postgres-extension work" idiom as [[routing]]'s `FOR UPDATE SKIP LOCKED`). 14 §2 scoring formula verbatim (0.75·similarity + 0.15·recency_decay(30d half-life) + 0.10·use-count-bonus, threshold 0.30); scope-set = this agent's `agent` rows ∪ its role's `role` rows ∪ all `company` rows (`task`-scope never cross-recalled); `use_count`/`last_used_at` bumped post-recall. **Design call — `MemoryStore`'s shape deviates from 14 §2's sketch:** no `browse()` method on the SPI — that's a plain filtered listing, implemented directly in new `MemoryService` over `MemoryRepository` (JPA) using the existing `PageEnvelope`/`KeysetCursors` keyset convention, only routing through `recall()` when a caller passes semantic `q`. **Second design call, the consequential one — memory recall runs a live embedding call INSIDE the claim's own transaction**, extending M-CTX1's "local-DB-only work" rule for the claimed-event enricher hook: `queryText` is task-specific (`task.title+description`), so it can only be embedded once `WorkBroker.claimNext` has picked a task, and `contextProvenance` must land in that SAME `claimed` event (03 invariant 1, append-only). Accepted as ~100-300ms added to the claim's row-lock hold time (documented in `PgVectorMemoryStore`'s class javadoc as the next lever — async pre-embedding — if it ever becomes a real bottleneck). `SkillContextAssembler` (kept its name — extending was less churn than renaming now, deferred to M-KN1) gained the memories step: `recall(k=12, queryText=task.title+description)` reordered preference/lesson-before-fact/summary then score desc, item-granular truncation at ≤35% of budget (no name+description fallback line the way skills has one — memory content is already short). Its own `@Transactional` lost `readOnly=true` (recall's use_count bump is a write; a readOnly method that STARTS rather than joins a transaction gets its JDBC connection set to actual Postgres read-only mode, which would break any direct/unit-style call to `assemble()`). New `MemoryService` (browse/seed/forget, 16 §3 — review-queue + review actions deliberately deferred to M-LN1, nothing produces `pending_review` memories yet) + `MemoryController`. New `MemoryTtlArchiver` (nightly, advisory-lock singleton matching `OutboxRetentionJob`'s shape — archives unused `lesson`/`summary` memories past `atrium.memory.ttl-days`, default 90). **Real bug found+fixed while testing:** `RestClient` on `SimpleClientHttpRequestFactory` (the exact recipe [[execution]]'s `GoogleClient` also uses) silently drops HTTP error response bodies in this Spring version — `OpenAiEmbeddingClient` uses `JdkClientHttpRequestFactory` instead (pinned to HTTP/1.1 — the JDK client's default h2c upgrade attempt is flaky against WireMock specifically, not a real-endpoint concern); the same bug in `GoogleClient` was flagged as a follow-up task rather than fixed inline (out of this milestone's scope). Done-when verified: seeding "CEO prefers bullet lists" as a company preference makes it appear in the next real LLM request under "## What you have learned here" (WireMock-captured); scope/status isolation (agent/company/pending-review/archived/rejected all correctly excluded from recall, 7 new test cases); recall stays under 100ms at 10k memories (dedicated perf test — the slow part was generating the 10k-row HNSW-indexed fixture, not the timed `recall()` call itself, fixed by doing that generation as one in-database SQL statement instead of a 10k-row JDBC batch). 110/110 core-api tests green (3 skipped, live-key tests + the new `OpenAiEmbeddingLiveTest`). `make check` clean.

**Earlier — CONTEXTASSEMBLER LIVE (M-CTX1, 2026-07-14 session 14).** `ContextAssembler` interface + `SkillContextAssembler` impl — skills-only v1 (14 §6 step 1); memories/knowledge slots (`MemoryHit`/`KnowledgeHit` placeholder records) stay empty until M-MEM1/M-KN1. Only `platform`/`company` trust-level skills are ever included (`agent_proposed` filtered out — no promotion path exists until M-LN1). `ContextBundle`/`SkillExcerpt`/`MemoryHit`/`KnowledgeHit` all live here (not in [[execution]]) since [[execution]] → agentmind is the allowed dependency direction (12 §2) and agentmind must never import execution types — `PromptAssembler` (execution) imports agentmind's `ContextBundle` as its `bundle` parameter type. **Claimed-event provenance wiring (the one real cross-module design call this milestone):** `task_events(claimed).payload.contextProvenance` must be written in the SAME transaction as the claim SQL + its audit event (03 invariant 1) — but [[routing]]'s `WorkBroker.claimNext` can't import agentmind's `ContextAssembler` (routing must not depend on agentmind/execution). **Earlier (M-SK1, 2026-07-14 session 13).** Schema was already live since M0.1 — `V2__agent_platform.sql` pasted the full 15 §§2–4 Rev C schema verbatim (skills/memories/knowledge tables all created then), so this milestone is Java/API only, no new DDL. `domain/`: `Skill` (versioned, `company_id NULL` = global platform skill, `UNIQUE(company_id, key, version)` — same versioning idiom as `RoleDefinition`), `RoleDefinitionSkill`/`AgentSkill` (composite-key join entities via `@IdClass`, first use of that pattern in the codebase). `SkillService`: CRUD + versioning (new version = new row, latest-per-`(company_id,key)` dedupe done in Java over an ordered query rather than JPQL window functions), attach/detach to agent, attach to role, and the `/mind` view assembly (memory/knowledge parts zeroed until M-MEM1/M-KN1). New `V5__seed_platform_skills.sql`: 2 platform skills per seeded template (coder: code-review-checklist + unified-diff-output; tester: test-coverage-checklist + bug-report-contract; research: source-ranking-procedure + summarization-contract), attached to their global `role_definitions` rows.

**Boundary decision — hire-time auto-attach without breaking the one-directional `agentmind → registry` dependency (12 §2):** `AgentService.hire()` (registry) needs to trigger a skill attach, but registry may not import agentmind types. Solved with a hook interface **owned by registry**: `registry.RoleSkillAttachment` (one method, `attachTemplateSkills`), implemented by agentmind's `SkillAttachmentService`. This keeps the only static import direction as `agentmind → registry` (agentmind implements a registry-owned interface) — same shape as `AgentDirectory`/`BudgetGuard`/`RoleDefinitionLookup`, just inverted: here the *consumer* (registry) owns the interface and the *provider* (agentmind) implements it, because the call originates in registry's hire flow. `RoleDefinitionLookup` gained a company-scoped `findVisibleToCompany` (agentmind needs it to validate the `/role-definitions/{id}/skills` attach endpoint's tenant ownership; the pre-existing `findById` had no company param since its only prior caller — PromptAssembler — already holds a trusted row).

**Design call — role-skill attach restricted to company-owned role definitions:** 16 §2's literal text doesn't restrict `POST /role-definitions/{id}/skills` to non-global role definitions, but role templates (`company_id NULL`) are ONE shared row every tenant hires from — attaching from company A's request would leak that skill into every other company's future hires from that template. `SkillService.attachToRole` requires `roleDefinition.companyId == companyId`, 404s on a global template id. Test: `attachToRoleOnlyAffectsCompanyOwnedRoleDefinition`.

**Key rules:** only `platform`/`company` trust-level skills may ever reach a prompt (`agent_proposed` skills — including the M-LN1 review-action "convert to draft skill" output — are inert until a human separately promotes them; no promotion path for `agent_proposed`→`platform`/`company` exists yet). Skills are versioned; attachments pin a specific version id, so a role's skill upgrade is an explicit re-attach, never automatic. `agent_skills.source`: `hired` (auto, from template) / `assigned` (manual attach) / `learned` (not produced yet — nothing attaches a skill to an agent automatically post-M-LN1 either; the draft-skill path creates the `Skill` row but doesn't attach it to anyone). Only `status='active'` memories may ever be recalled into a prompt; `pending_review` memories now have a real path to `active` via `POST /memories/{id}/review` (M-LN1); `rejected`/`archived` stay permanently excluded. `forget` always archives, never hard-deletes (09 audit posture).
