# agentmind

**What:** [[core-api]] module owning the skills registry (14 §1) — the first slice of the "depth" subsystem ([[agent-platform]]: skills → memory → knowledge → learning). Future milestones (M-MEM1/M-KN1/M-LN1) add MemoryStore, knowledge ingestion, and the learning pipeline into this same module.

**State: CONTEXTASSEMBLER LIVE (M-CTX1, 2026-07-14 session 14).** `ContextAssembler` interface + `SkillContextAssembler` impl — skills-only v1 (14 §6 step 1); memories/knowledge slots (`MemoryHit`/`KnowledgeHit` placeholder records) stay empty until M-MEM1/M-KN1. Deterministic assembly: role-attached ("hired") skills in the role's `position` order, then the agent's own ("assigned"/"learned") skills by proficiency desc (tiebreak: attachedAt, then skillId); item-granular truncation under a token budget (`runtime_config.contextBudgetTokens` default 4000, hard-capped at 30% of the model's catalog context window) — whole `body_md` if it fits, else a name+description index-line fallback, else the item is dropped and the loop keeps trying subsequent (possibly smaller) items; chars/4 token-estimation heuristic. Only `platform`/`company` trust-level skills are ever included (`agent_proposed` filtered out — no promotion path exists until M-LN1). `ContextBundle`/`SkillExcerpt`/`MemoryHit`/`KnowledgeHit` all live here (not in [[execution]]) since [[execution]] → agentmind is the allowed dependency direction (12 §2) and agentmind must never import execution types — `PromptAssembler` (execution) imports agentmind's `ContextBundle` as its `bundle` parameter type. **Claimed-event provenance wiring (the one real cross-module design call this milestone):** `task_events(claimed).payload.contextProvenance` must be written in the SAME transaction as the claim SQL + its audit event (03 invariant 1) — but [[routing]]'s `WorkBroker.claimNext` can't import agentmind's `ContextAssembler` (routing must not depend on agentmind/execution). Solved by adding a plain-JDK `Function<Task, ObjectNode>` enricher parameter to `claimNext`, invoked inside its existing transaction; [[execution]]'s `LlmLoopRuntime` passes a lambda that calls `ContextAssembler.assemble` once, captures the resulting bundle into a one-element array (reused for the prompt — no second assemble() call), and returns `{contextProvenance:[...]}` for the enricher to merge into the claimed event's payload. `PromptAssembler`'s layout gained a "## Your skills" system-prompt section (rendered from `bundle.skills()`); "## What you have learned here"/"## Reference material" are deliberately NOT rendered yet (would be dead code — `bundle.memories()`/`bundle.knowledge()` are always empty this milestone). Done-when verified: 7 unit-style tests (fits-all, name+description fallback, item-granular truncation skipping oversized items while still including smaller ones after, role-then-proficiency ordering, `agent_proposed` never reaches the bundle, budget resolution, determinism) plus an integration test on a real claim→LLM→pending_review run showing the claimed event's `contextProvenance` array and a WireMock-captured prompt containing "## Your skills". 90/90 core-api tests green (2 skipped, live-key tests unchanged). `make check` clean.

**Earlier (M-SK1, 2026-07-14 session 13).** Schema was already live since M0.1 — `V2__agent_platform.sql` pasted the full 15 §§2–4 Rev C schema verbatim (skills/memories/knowledge tables all created then), so this milestone is Java/API only, no new DDL. `domain/`: `Skill` (versioned, `company_id NULL` = global platform skill, `UNIQUE(company_id, key, version)` — same versioning idiom as `RoleDefinition`), `RoleDefinitionSkill`/`AgentSkill` (composite-key join entities via `@IdClass`, first use of that pattern in the codebase). `SkillService`: CRUD + versioning (new version = new row, latest-per-`(company_id,key)` dedupe done in Java over an ordered query rather than JPQL window functions), attach/detach to agent, attach to role, and the `/mind` view assembly (memory/knowledge parts zeroed until M-MEM1/M-KN1). New `V5__seed_platform_skills.sql`: 2 platform skills per seeded template (coder: code-review-checklist + unified-diff-output; tester: test-coverage-checklist + bug-report-contract; research: source-ranking-procedure + summarization-contract), attached to their global `role_definitions` rows.

**Boundary decision — hire-time auto-attach without breaking the one-directional `agentmind → registry` dependency (12 §2):** `AgentService.hire()` (registry) needs to trigger a skill attach, but registry may not import agentmind types. Solved with a hook interface **owned by registry**: `registry.RoleSkillAttachment` (one method, `attachTemplateSkills`), implemented by agentmind's `SkillAttachmentService`. This keeps the only static import direction as `agentmind → registry` (agentmind implements a registry-owned interface) — same shape as `AgentDirectory`/`BudgetGuard`/`RoleDefinitionLookup`, just inverted: here the *consumer* (registry) owns the interface and the *provider* (agentmind) implements it, because the call originates in registry's hire flow. `RoleDefinitionLookup` gained a company-scoped `findVisibleToCompany` (agentmind needs it to validate the `/role-definitions/{id}/skills` attach endpoint's tenant ownership; the pre-existing `findById` had no company param since its only prior caller — PromptAssembler — already holds a trusted row).

**Design call — role-skill attach restricted to company-owned role definitions:** 16 §2's literal text doesn't restrict `POST /role-definitions/{id}/skills` to non-global role definitions, but role templates (`company_id NULL`) are ONE shared row every tenant hires from — attaching from company A's request would leak that skill into every other company's future hires from that template. `SkillService.attachToRole` requires `roleDefinition.companyId == companyId`, 404s on a global template id. Test: `attachToRoleOnlyAffectsCompanyOwnedRoleDefinition`.

**Key rules:** only `platform`/`company` trust-level skills may ever reach a prompt (`agent_proposed` is inert until a human promotes it — not built yet, no promotion path exists until M-LN1). Skills are versioned; attachments pin a specific version id, so a role's skill upgrade is an explicit re-attach, never automatic. `agent_skills.source`: `hired` (auto, from template) / `assigned` (manual attach) / `learned` (not produced yet — M-LN1).

**Done-when verified:** hire from `coder`/`research` templates → `/agents/{id}/mind` shows exactly the template's skills with `source:"hired"`; attach a custom company skill → appears with `source:"assigned"` + given proficiency, detach removes it, hired skills untouched; two companies each see all 6 global skills + only their own custom skill in `GET /companies/{id}/skills`, `kind` filter works, versioning shows latest-only with correct dedup, cross-company version-attempt 404s. 82/82 core-api tests green (2 skipped, live-key tests unchanged). `make check` clean.
