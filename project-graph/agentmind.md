# agentmind

**What:** [[core-api]] module owning the skills registry (14 §1) and, as of this session, the memory store (14 §2) — the "depth" subsystem ([[agent-platform]]: skills → memory → knowledge → learning). Future milestones (M-LN1/M-KN1) add the learning pipeline and knowledge ingestion into this same module.

**State: MEMORY STORE + RECALL LIVE (M-MEM1, 2026-07-15 session 15).** `EmbeddingClient` SPI + `OpenAiEmbeddingClient` (REST, key `OPENAI_API_KEY`, default `text-embedding-3-small`/1536-dim) — `isReady()` false means degrade, never throw, same pre-dispatch-gate contract as [[execution]]'s `ProviderReadiness` but added directly to this (non-frozen) interface. `PgVectorMemoryStore implements MemoryStore` (ingest/recall/forget/setStatus) — raw JDBC throughout, no Hibernate vector-type mapping (the `Memory` entity excludes the `embedding` column entirely; only this class ever reads/writes pgvector text literals, cast via `::vector` in SQL — same "raw SQL for Postgres-extension work" idiom as [[routing]]'s `FOR UPDATE SKIP LOCKED`). 14 §2 scoring formula verbatim (0.75·similarity + 0.15·recency_decay(30d half-life) + 0.10·use-count-bonus, threshold 0.30); scope-set = this agent's `agent` rows ∪ its role's `role` rows ∪ all `company` rows (`task`-scope never cross-recalled); `use_count`/`last_used_at` bumped post-recall. **Design call — `MemoryStore`'s shape deviates from 14 §2's sketch:** no `browse()` method on the SPI — that's a plain filtered listing, implemented directly in new `MemoryService` over `MemoryRepository` (JPA) using the existing `PageEnvelope`/`KeysetCursors` keyset convention, only routing through `recall()` when a caller passes semantic `q`. **Second design call, the consequential one — memory recall runs a live embedding call INSIDE the claim's own transaction**, extending M-CTX1's "local-DB-only work" rule for the claimed-event enricher hook: `queryText` is task-specific (`task.title+description`), so it can only be embedded once `WorkBroker.claimNext` has picked a task, and `contextProvenance` must land in that SAME `claimed` event (03 invariant 1, append-only). Accepted as ~100-300ms added to the claim's row-lock hold time (documented in `PgVectorMemoryStore`'s class javadoc as the next lever — async pre-embedding — if it ever becomes a real bottleneck). `SkillContextAssembler` (kept its name — extending was less churn than renaming now, deferred to M-KN1) gained the memories step: `recall(k=12, queryText=task.title+description)` reordered preference/lesson-before-fact/summary then score desc, item-granular truncation at ≤35% of budget (no name+description fallback line the way skills has one — memory content is already short). Its own `@Transactional` lost `readOnly=true` (recall's use_count bump is a write; a readOnly method that STARTS rather than joins a transaction gets its JDBC connection set to actual Postgres read-only mode, which would break any direct/unit-style call to `assemble()`). New `MemoryService` (browse/seed/forget, 16 §3 — review-queue + review actions deliberately deferred to M-LN1, nothing produces `pending_review` memories yet) + `MemoryController`. New `MemoryTtlArchiver` (nightly, advisory-lock singleton matching `OutboxRetentionJob`'s shape — archives unused `lesson`/`summary` memories past `atrium.memory.ttl-days`, default 90). **Real bug found+fixed while testing:** `RestClient` on `SimpleClientHttpRequestFactory` (the exact recipe [[execution]]'s `GoogleClient` also uses) silently drops HTTP error response bodies in this Spring version — `OpenAiEmbeddingClient` uses `JdkClientHttpRequestFactory` instead (pinned to HTTP/1.1 — the JDK client's default h2c upgrade attempt is flaky against WireMock specifically, not a real-endpoint concern); the same bug in `GoogleClient` was flagged as a follow-up task rather than fixed inline (out of this milestone's scope). Done-when verified: seeding "CEO prefers bullet lists" as a company preference makes it appear in the next real LLM request under "## What you have learned here" (WireMock-captured); scope/status isolation (agent/company/pending-review/archived/rejected all correctly excluded from recall, 7 new test cases); recall stays under 100ms at 10k memories (dedicated perf test — the slow part was generating the 10k-row HNSW-indexed fixture, not the timed `recall()` call itself, fixed by doing that generation as one in-database SQL statement instead of a 10k-row JDBC batch). 110/110 core-api tests green (3 skipped, live-key tests + the new `OpenAiEmbeddingLiveTest`). `make check` clean.

**Earlier — CONTEXTASSEMBLER LIVE (M-CTX1, 2026-07-14 session 14).** `ContextAssembler` interface + `SkillContextAssembler` impl — skills-only v1 (14 §6 step 1); memories/knowledge slots (`MemoryHit`/`KnowledgeHit` placeholder records) stay empty until M-MEM1/M-KN1. Deterministic assembly: role-attached ("hired") skills in the role's `position` order, then the agent's own ("assigned"/"learned") skills by proficiency desc (tiebreak: attachedAt, then skillId); item-granular truncation under a token budget (`runtime_config.contextBudgetTokens` default 4000, hard-capped at 30% of the model's catalog context window) — whole `body_md` if it fits, else a name+description index-line fallback, else the item is dropped and the loop keeps trying subsequent (possibly smaller) items; chars/4 token-estimation heuristic. Only `platform`/`company` trust-level skills are ever included (`agent_proposed` filtered out — no promotion path exists until M-LN1). `ContextBundle`/`SkillExcerpt`/`MemoryHit`/`KnowledgeHit` all live here (not in [[execution]]) since [[execution]] → agentmind is the allowed dependency direction (12 §2) and agentmind must never import execution types — `PromptAssembler` (execution) imports agentmind's `ContextBundle` as its `bundle` parameter type. **Claimed-event provenance wiring (the one real cross-module design call this milestone):** `task_events(claimed).payload.contextProvenance` must be written in the SAME transaction as the claim SQL + its audit event (03 invariant 1) — but [[routing]]'s `WorkBroker.claimNext` can't import agentmind's `ContextAssembler` (routing must not depend on agentmind/execution). Solved by adding a plain-JDK `Function<Task, ObjectNode>` enricher parameter to `claimNext`, invoked inside its existing transaction; [[execution]]'s `LlmLoopRuntime` passes a lambda that calls `ContextAssembler.assemble` once, captures the resulting bundle into a one-element array (reused for the prompt — no second assemble() call), and returns `{contextProvenance:[...]}` for the enricher to merge into the claimed event's payload. `PromptAssembler`'s layout gained a "## Your skills" system-prompt section (rendered from `bundle.skills()`); "## What you have learned here"/"## Reference material" are deliberately NOT rendered yet (would be dead code — `bundle.memories()`/`bundle.knowledge()` are always empty this milestone). Done-when verified: 7 unit-style tests (fits-all, name+description fallback, item-granular truncation skipping oversized items while still including smaller ones after, role-then-proficiency ordering, `agent_proposed` never reaches the bundle, budget resolution, determinism) plus an integration test on a real claim→LLM→pending_review run showing the claimed event's `contextProvenance` array and a WireMock-captured prompt containing "## Your skills". 90/90 core-api tests green (2 skipped, live-key tests unchanged). `make check` clean.

**Earlier (M-SK1, 2026-07-14 session 13).** Schema was already live since M0.1 — `V2__agent_platform.sql` pasted the full 15 §§2–4 Rev C schema verbatim (skills/memories/knowledge tables all created then), so this milestone is Java/API only, no new DDL. `domain/`: `Skill` (versioned, `company_id NULL` = global platform skill, `UNIQUE(company_id, key, version)` — same versioning idiom as `RoleDefinition`), `RoleDefinitionSkill`/`AgentSkill` (composite-key join entities via `@IdClass`, first use of that pattern in the codebase). `SkillService`: CRUD + versioning (new version = new row, latest-per-`(company_id,key)` dedupe done in Java over an ordered query rather than JPQL window functions), attach/detach to agent, attach to role, and the `/mind` view assembly (memory/knowledge parts zeroed until M-MEM1/M-KN1). New `V5__seed_platform_skills.sql`: 2 platform skills per seeded template (coder: code-review-checklist + unified-diff-output; tester: test-coverage-checklist + bug-report-contract; research: source-ranking-procedure + summarization-contract), attached to their global `role_definitions` rows.

**Boundary decision — hire-time auto-attach without breaking the one-directional `agentmind → registry` dependency (12 §2):** `AgentService.hire()` (registry) needs to trigger a skill attach, but registry may not import agentmind types. Solved with a hook interface **owned by registry**: `registry.RoleSkillAttachment` (one method, `attachTemplateSkills`), implemented by agentmind's `SkillAttachmentService`. This keeps the only static import direction as `agentmind → registry` (agentmind implements a registry-owned interface) — same shape as `AgentDirectory`/`BudgetGuard`/`RoleDefinitionLookup`, just inverted: here the *consumer* (registry) owns the interface and the *provider* (agentmind) implements it, because the call originates in registry's hire flow. `RoleDefinitionLookup` gained a company-scoped `findVisibleToCompany` (agentmind needs it to validate the `/role-definitions/{id}/skills` attach endpoint's tenant ownership; the pre-existing `findById` had no company param since its only prior caller — PromptAssembler — already holds a trusted row).

**Design call — role-skill attach restricted to company-owned role definitions:** 16 §2's literal text doesn't restrict `POST /role-definitions/{id}/skills` to non-global role definitions, but role templates (`company_id NULL`) are ONE shared row every tenant hires from — attaching from company A's request would leak that skill into every other company's future hires from that template. `SkillService.attachToRole` requires `roleDefinition.companyId == companyId`, 404s on a global template id. Test: `attachToRoleOnlyAffectsCompanyOwnedRoleDefinition`.

**Key rules:** only `platform`/`company` trust-level skills may ever reach a prompt (`agent_proposed` is inert until a human promotes it — not built yet, no promotion path exists until M-LN1). Skills are versioned; attachments pin a specific version id, so a role's skill upgrade is an explicit re-attach, never automatic. `agent_skills.source`: `hired` (auto, from template) / `assigned` (manual attach) / `learned` (not produced yet — M-LN1). Only `status='active'` memories may ever be recalled into a prompt; `pending_review`/`rejected`/`archived` are inert until M-LN1's review governance gives them a path to `active` (or, for `archived`, they're just gone from recall permanently). `forget` always archives, never hard-deletes (09 audit posture).
